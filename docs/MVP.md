# MVP：一项任务的验收准备

目标用户：在本地 Git worktree 中让 coding agent 实现修改，完成后自己看 diff 和验证材料的开发者。

触发：准备检查尚未提交的修改。结果：打开同一份需求、当前 diff 和有出处的检查记录，明确哪些证据缺失或对应旧代码。

本版只有一个插件。已有 reviewr 负责深入看 diff，已有 review-loop 负责自动审核；不重复其功能。借鉴其 pane/action 与仓库定位方式，不复制其实现代码。

## 本版实现

- `begin --brief`：显式绑定需求文件并保存内容快照，生成任务身份。
- `check -- COMMAND`：仅执行用户指定的命令，保存退出码、有限日志、运行前后代码指纹。
- `pack`：生成 Markdown、JSON 与 HEAD diff；显示新鲜度与缺失材料。
- Herdr 手动 popup：查看需求、diff、检查日志；无需 LLM、守护进程或构建依赖。

需求输入先用文件，避免自动选错会话或把压缩摘要当原始要求。MVP 不读取 transcript。自动导入一个明确指定的 Claude 会话，仅在用户反馈手工准备 brief 是主要成本时再考虑。

## 不包含

自动质量评分、接管/审核调度、通知收件箱、跨机同步、自动运行测试、多任务共用 worktree、已提交或 last-turn diff、submodule、全环境可复现证明。

## 发布前验收

1. 小型临时 Git 项目：begin → 修改 → check → pack，能看到对应命令及日志。
2. 修改代码、索引或非忽略新文件后，旧证据不能继续显示 same-snapshot。
3. 失败、超时、日志丢失、检查期间修改、无证据均明确呈现；不变成“通过”。
4. 新任务不能继承旧任务证据，插件导出不能修改被验收仓库。
5. Herdr 0.9.0 中 link → action → popup → 查看 → 关闭 → unlink 实测通过。
6. 说明安装、卸载、数据位置、日志上限和已知边界；发布包不含用户数据。

## 研究策略（2026-09-09 决定）

不做访谈项目，直接发布 alpha，以真实安装与反馈作为需求信号。`docs/research/2026-09-09-field-study-kit.md` 保留为备选方案，未执行。如果发布 4 周后既无安装反馈也无问题报告，再决定是否启用访谈或停止。

## 上架后的最小学习循环

发布 alpha 后先收集 3–5 位真实试用者的具体反馈：是否在第二个任务继续使用；是否少了找需求/日志的步骤；是否因需要额外包装命令而放弃。没有反馈先检查是否有人安装，不直接判定无需求。

保留：重复使用且能举出省去的动作。修改：价值明确但记录步骤繁琐。停止或并入其他插件：只需要已有工具加一段说明，或重复反馈收益不抵操作成本。不做正式访谈项目，不添加默认遥测。
